# 视频总结：用工程环境建立对 Agent 的信任

来源：[@poteto 分享的原视频](https://x.com/poteto/status/2102050467505430555)。本文根据维护者提供的中文字幕整理，是对观点的归纳，不是完整字幕或演讲者的官方文档；专有名词和图示细节仍以原视频为准。

## 核心观点

每次需要纠正 Agent 时，不只解决眼前错误，还应思考：应该改变哪一层工程环境，才能让下一个 Agent 更容易做对？投入优先级是 **Codebase → Static Analysis → Rules / BugBot → Skills → Style Guide**。优先级强调约束的可靠性与复用价值，不是逐项实施的固定清单。

## 1. Codebase：把经验落实到正确的默认路径

代码库本身是一种记忆。Agent 会读取、沿用已有模式，统一且安全的入口能够传播，临时补丁与坏模式也会被复制。

优先考虑通过 API、数据结构、模块边界和进程分工减少误用。不是每个问题都值得重构整个系统；目标是让当前问题的正确实现成为低摩擦路径。持续清理不希望被复制的反模式，比不断追加提醒更有长期价值。

LoopLab 的具体实践：新建和编辑记忆都经过 `server.py` 的 `create_memory`，由共享入口拒绝“已验证但证据为空”；数据库调用统一经过负责事务与关闭的 `dbconnect`。

## 2. Static Analysis：让可机械识别的错误被自动发现

将稳定、明确的约束变成 lint、类型或编译器诊断、依赖边界检查。CI 是运行检查的自动化机制，并不等同于静态分析。

当架构调整暂时成本过高时，检查也能先阻止坏模式继续扩散。必须验证错误示例会失败，合法使用能通过。运行时回归测试同样重要，但不能把它称为静态分析。

LoopLab 当前有运行时校验和回归测试，尚未实现专用架构 lint 或 CI 阻断。

## 3. Rules / BugBot：用指导和审查补充硬约束

Rules 指导 Agent 的行为，BugBot 一类审查工具检查修改结果。它们适合部分依赖语义判断的问题，但规则可能未被读取，AI 审查也可能漏报，因此不能代替代码或自动检查。

一条有效规则应明确场景、要求和可审查的例子。不要把每次纠错都变成更多规则文档。

## 4. Skills：把验证变成可重复执行的方法

视频重点讨论的验证技能由两部分组成：

- **稳定工具 / CLI**：以一致方式运行应用、复现问题、采集 trace 和性能证据。
- **功能地图**：描述功能入口、交互步骤、预期状态、实现位置与验证方式，让 Agent 能从模糊报告定位实际行为。

功能正确性、性能和代码质量需要不同证据。单纯保存流程说明、看见 trace 或通过语法检查，都不能证明业务功能正确。

LoopLab 保留可复用的 HTTP 检查脚本与[功能地图](feature-map.md)，本次发布不分发可安装 skill。

## 5. Style Guide：用作原则，不把人工记忆作为唯一防线

风格指南适合记录设计取舍和团队约定，但仅靠人工逐行审查，难以应对大量 Agent 产出的修改。可以从反复出现的审查意见中提炼更强的 API、检查或工作流程。

能自动验证的规范应尽量自动化；确实需要判断的取舍保留正反例与适用范围。

## 视频与本项目的边界

- 视频中的 Dune 体现了将推荐模式和导入 / 进程边界固化在框架里的思路，不是所有项目都要复制的目录结构。
- 特定团队禁止代码注释是针对其具体问题的选择，不能泛化成所有仓库都禁止注释。
- “完整录制每个 Agent、代码行归属、重试可视化”是另外的产品能力，不是实现五层思路的必要条件。
- LoopLab 的 Retry Dashboard 与 JSON 工程记忆是本项目的实践设计，不是原视频产品的复刻，也不表示获得原作者背书。
